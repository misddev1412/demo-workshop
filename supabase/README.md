`tests/access_control.sql` passed via MCP and rolls back all fixtures.
It checks anonymous catalog access, blocked anonymous order access, ordinary
user order isolation, admin order access/update, blocked allowlist enrollment
(including by application admins), positive quantity, nonnegative prices/totals,
and order/product foreign keys. This tests PostgreSQL roles and Auth claims,
not the browser sign-in flow.

All four tables have RLS enabled. The private allowlist intentionally has no
client policies or table privileges. No user is automatically made an admin.
Only the project owner using privileged SQL should add an existing Supabase Auth
user ID:

```sql
insert into shop_private.admin_allowlist (user_id)
values ('<existing-auth-user-uuid>'::uuid)
on conflict (user_id) do nothing;
```

Ordinary clients cannot directly create orders. `POST /api/orders` now calls the
service-only `place_cod_order(jsonb)` RPC, which validates products and computes
prices/totals before atomically writing orders and items.

Security advisor results: INFO for the deliberately policy-free private
allowlist, and two WARN findings on pre-existing `public.rls_auto_enable()`
being executable by anon/authenticated. That function was not changed here.
See https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable
